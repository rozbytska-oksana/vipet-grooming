# Перегляд на GitHub Pages

Репозиторій — https://github.com/rozbytska-oksana/vipet-grooming.
Очікувана адреса після публікації — https://rozbytska-oksana.github.io/vipet-grooming/.

Це production-оптимізована статична версія для погодження власницею.
SSR-контент зберігається у згенерованому HTML. Для перегляду діє noindex,nofollow.
Індексація комерційного сайту потребує окремого рішення й перевіреного домену.
Публічна адреса доступна кожному, хто має посилання. noindex не обмежує доступ.

## Локальна збірка

Використати Node із .nvmrc та вже встановлені залежності.

```sh
npm run generate:pages
```

Результат знаходиться в `.output-pages/public`, проміжні файли — у `.nuxt-pages`.
Звичайні dev та HostPro-команди продовжують використовувати свої каталоги.
Типовий base path — `/vipet-grooming/`. Для перевірки кореневого розміщення можна
запустити `NUXT_APP_BASE_URL=/ npm run generate:pages`.

Команда примусово вимикає реальне надсилання заявок та індексацію незалежно від локального .env.
Соцпрев’ю використовує фактичний HTTPS origin Pages, заданий VIPET_PAGES_ORIGIN.
Форма дозволяє заповнення та валідацію. PHP API й каталог API вилучаються лише
з готового Pages-артефакту. Приватні файли й токен не потрібно додавати в GitHub.
Для Telegram на HostPro залишається окремий обробник з BOOKING_TELEGRAM_SETUP.md.
GitHub Pages PHP не виконує.

## Ручна публікація після погодження

1. Додати зміни проєкту до вказаного репозиторію. Публікація з локальної папки
   автоматично не виконується. Перед комітом перевірити список файлів і .gitignore.
   Окремий Git remote у цій робочій папці поки не налаштований.
2. У Settings → Pages вибрати Source → GitHub Actions.
3. В Actions відкрити Publish GitHub Pages review та натиснути Run workflow.
4. Дочекатися успішних build і deploy, відкрити адресу з deployment environment.

Workflow має тільки ручний тригер. base path отримується з конфігурації Pages.
CI встановлює залежності через npm ci із lockfile, запускає тести та генерацію,
передає лише `.output-pages/public` до офіційного Pages deployment action.
Секрети Telegram для цього workflow не потрібні.

## Перевірка опублікованого результату

Перевірити головну сторінку й пряме оновлення, favicon, локальні шрифти, зображення,
каруселі, повні сертифікати, відео, переходи до секцій, мобільне меню та валідацію
форми. Неіснуючий URL має повертати сторінку 404 зі статусом 404.
Перевірити noindex у HTML і відсутність запитів форми до PHP.
Після майбутньої публікації ці перевірки потрібно повторити на реальному хості.

## Формати зображень

Для більшості фотографій `<picture>` пропонує AVIF і WebP. Браузер вибирає перший
підтримуваний формат. Для логотипів, SVG-декору та повнорозмірних сертифікатів
використовуються відповідні наявні WebP, PNG та SVG.

Кодування AVIF виконується під час підготовки ресурсів. Браузер декодує готовий
файл. Ефективність залежить від пристрою, розміру та конкретного зображення.
Розміри srcset/sizes, відкладене завантаження нижніх секцій і пріоритет Hero
залишаються важливими незалежно від формату. Вибір між AVIF і WebP у `<picture>`
залежить від підтримки, а не від автоматичної оцінки швидкості декодування.
